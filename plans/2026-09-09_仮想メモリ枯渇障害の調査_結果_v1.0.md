# 2026-09-09 仮想メモリ枯渇障害の調査 結果 v1.0

調査対象: Windows の仮想メモリ（システム コミット）が枯渇した場合、およびページファイル配置ドライブの空きがなくなった場合の障害。
推測で障害名は書いていない。根拠は公式ドキュメントと Microsoft サポート記事。

## 結論

仮想メモリ枯渇の本体は「物理 RAM が空いているかどうか」ではなく、**システム コミット制限（Commit Limit = RAM + 全ページファイル）にコミット済み量が達すること**。達すると新規のメモリ確保が拒否され、アプリが落ちる・固まる・不定動作になる。

ページファイル配置ドライブの空きがなくなると、システム管理のページファイルが伸びられず、コミット制限が上がらない。その結果、同じ枯渇状態に入る。Microsoft 自身が「成長には十分な空きディスク領域が必要」と明記している。

## ページファイル配置ドライブが満杯のとき

Microsoft の制約:

- システム管理ページファイルは、コミット使用が制限の 90% に達すると自動拡張する。上限は「RAM の 3 倍」または 4 GB の大きい方。さらに **ボリュームサイズの 1/8** で頭打ち。クラッシュダンプ要件がある場合は空きが 1 GB 以内まで伸びることがある。
- いずれも前提は **「成長を収容できる十分な空きディスク領域があること」**。
- 起動時のシステム管理サイズも「十分な空きディスク領域が存在することを前提」。

空きが無い場合に起きること（公式の因果）:

1. ページファイルが伸びない → コミット制限が上がらない。
2. コミット済み量が制限に達する → 以降の `VirtualAlloc` 等が失敗。
3. 自動拡張中でも「一部アプリのメモリ要求が拒否される」。
4. 拡張そのものが遅いと、空きがあってもランダム OOM になる（KB 4055223。フィルタードライバ等の I/O 遅延）。空きゼロなら拡張はさらに失敗する。
5. クラッシュ時に Memory.dmp を書けない。完全ダンプは RAM + 257 MB が必要。
6. ページファイル使用率 100% は「things will stop working」（古いサーバー文書の表現）。

悪循環:

- コミット増 → pagefile.sys 膨張 → 配置ドライブの空き消滅 → ページファイルも他の書き込みも止まる → Windows Update やログ、ダンプまで失敗。

## 見分け方（公式）

- タスク マネージャー → パフォーマンス → メモリの「コミット済み / 制限」。
- カウンター `\Memory\Committed Bytes` と `\Memory\Commit Limit`、`\Memory\% Committed Bytes In Use`。
- `\Paging Files(*)\% Usage`。
- イベント ビューアー: ソース `Microsoft-Windows-Resource-Exhaustion-Detector`、ID 2004。上位 3 プロセスが出る。原因そのものではなく、その時点の上位消費者。
- 詳細タブの ProcessCommitCharge / PagedPoolUsage / NonPagedPoolUsage（MS Japan ブログの Case 1〜3）。
- RAM 使用率が低くてもコミットが上限なら枯渇。見た目の「空き RAM」では判断しない。
