# 計画書: QuickDiskRescue 初期実装(v1.0)

## 目的

Windows がレターを付けず、パーティション容量表示が狂い、マウントできないディスクから、**書き込まずに中身を診断し、別ディスクへイメージ／ファイルを救い出す**アプリを自作する。EaseUS / MiniTool 等の有料・広告付き復旧ソフトの代替を、今回起きた障害（仮想メモリ枯渇クラッシュ後の D: 消失、1TB が 2TB と出る、復旧は別 PC）に絞って作る。

## 現状分析

- リポジトリ: `C:\Users\0120025-Z100\source\project\QuickDiskRescue`
- `git init` 済み。中身は `plans/` のみ。アプリコード・テンプレート未展開。
- 調査済み:
  - 仮想メモリ枯渇はコミット制限到達。pagefile 配置ドライブ満杯で拡張不能。
  - pagefile.sys 単体破損ではドライブ非認識・容量倍増は説明できない。
  - 空きゼロ + 不完全シャットダウンで NTFS dirty / RAW、GPT primary/backup 不一致は実在する。
- 流用できる自前資産: QuickFolderSize の NTFS MFT 読み（ただし **マウント済み `\\.\X:`**）。本アプリは **未マウント `\\.\PhysicalDriveN` + パーティションオフセット** が必要で、そのままは使えない。
- 系列制約: `___appli-template`。C++17 + WebView2、ダーク UI、日英、MIT、制作者 maktak-105。新規 WebMessage キーは `type`。管理者必須は製品の売りがあるときだけ → 本アプリは raw ディスク読みが売りなので `requireAdministrator` にする。
- Git commit / push は本計画に含めない。

## 製品定義（v1.0 でやること）

日本語名: **ディスク救出**  
EXE: `QuickDiskRescue.exe`  
初期バージョン: `1.0.0`  
方式: C++17 / MinGW-w64 / WebView2（Quick 本線）。CLI `QuickDiskRescue_cli.exe` あり。  
サードパーティ C++ ライブラリは入れない。TestDisk / PhotoRec / The Sleuth Kit は GPL 混入になるので **同梱しない・リンクしない**。

### 対象シナリオ（今回の事故）

別 PC に壊れたディスクを接続した状態。

1. 物理ディスクは見えるがエクスプローラーに D: が出ない。
2. パーティションは見えるがサイズが実容量と違う（1TB なのに 2TB 等）。
3. ファイルシステムが RAW / 不明 / レターなし。
4. NTFS の $Boot または $MFT がセクター単位では残っている。

### v1.0 の機能

| 機能 | 内容 | 書き込み |
|---|---|---|
| ディスク列挙 | `\\.\PhysicalDriveN`、容量、セクタサイズ、バス、オンライン状態 | なし |
| パーティション診断 | MBR / Protective MBR / GPT primary・backup を両方読む。LBA・CRC・LastUsableLBA・実ディスクセクタ数の不一致を表示 | なし |
| ファイルシステム検出 | 各パーティション先頭と NTFS バックアップブート（ボリューム末尾）のシグネチャ | なし |
| 診断レポート | 上記を画面表示し、Markdown / JSON で保存（保存先は健全な別ドライブのみ） | 別ドライブへ |
| ディスクイメージ | ソースを読み取り専用で開き、別ディスク上の `.img` へコピー。進捗・ハッシュ。不良セクタはゼロ埋めして続行しログに残す | ソースへはしない |
| ファイル救出 | イメージまたは物理ディスク上で $MFT が解釈できるとき、ツリー表示して選択ファイルを別ドライブへコピー | ソースへはしない |
| レター割り当て | ボリュームが実際には NTFS として健全で、レターが無いだけのとき、ユーザー確認後にレター付与 | レジストリ/マウントのみ。ディスク内容は触らない |

既定は常に読み取り専用。イメージ未作成のディスクに対する修復書き込み UI は出さない。

### v1.0 でやらないこと

- GPT ヘッダ修復、NTFS バックアップブートの書き戻し、dirty bit クリア（**v1.1 以降、イメージ成功後・三重確認**）
- 削除済みファイルの本格復旧、シグネチャ・カービング（JPEG/PDF 全ディスク走査）
- BitLocker / ReFS / Storage Spaces / 動的ディスク / RAID
- 不良セクタのリマップ、ファームウェア操作
- 初期化・フォーマット・パーティション新規作成（画面にも出さない）
- 広告、オンライン認証、テレメトリ

EaseUS 互換は謳わない。README に「診断・イメージ・MFT が読める場合のファイルコピー」と明記する。

## 画面構成

Quick 共通ダーク UI（`11_アプリ仕様.md`）。

```
┌─ ファイル / ヘルプ ────────────────────────── [🌐 日本語] ─┐
├─ ディスク一覧（左）─┬─ 診断結果（メイン）                    ┤
│ PhysicalDrive0    │  容量 / GPT primary vs backup / 差分   │
│ PhysicalDrive1    │  パーティション表（開始LBA, 終了, FS）   │
│ （イメージを開く） │  NTFS $Boot / backup boot / MFT 可否    │
│                   ├─ [診断] [イメージ保存] [ファイルを見る]  │
│ 経過時間          │  ファイルツリー（MFT可のとき）           │
└───────────────────┴─ ステータス: 読取専用 / 進捗 / 警告 ────┘
```

- タイトルバーに「読取専用」を常時表示。
- 保存先ピッカーはネイティブダイアログを検査で必須にしない。`--open` と `{type:"set_output", path}` で指定可能（`10_検査容易性ルール.md`）。
- 破壊的操作のボタンは v1.0 に置かない。
- ヘルプ → バージョン情報（ワッペン `assets/maktak105-V04-01.jpg`、幅 160px）。
- WebMessage は `{type: ...}` JSON。`ping`/`pong`。`QUICKAPPSTEST=1`。安定 `id`。

## エンジン設計

`core/native/` に GUI 非依存で置く。テストは合成ディスクイメージ（小さな GPT + NTFS）で回す。ユーザーの実ディスクは計画上の検証対象にしない（別 PC で復旧中のため）。

1. `disk_enum` — `SetupDi` / `IOCTL_STORAGE_GET_DEVICE_NUMBER` / `IOCTL_DISK_GET_DRIVE_GEOMETRY_EX` / `IOCTL_DISK_GET_LENGTH_INFO`
2. `gpt_parse` — LBA0 protective MBR、LBA1 header、partition array、末尾 backup。CRC32、MyLBA、AlternateLBA、LastUsableLBA、実サイズ比較。不一致を構造化して返す（1TB vs 2TB の本丸）
3. `mbr_parse` — 通常 MBR も読む
4. `fs_probe` — パーティション開始セクタで NTFS/FAT/exFAT マジック。NTFS なら BPB からセクタ/クラスタ、$MFT 開始、バックアップブート位置
5. `imager` — ソース `GENERIC_READ`、出力はユーザー指定パス。4MiB 単位。失敗 LBA を記録してスキップ
6. `mft_walk` — 未マウント NTFS の $MFT データランを追い、FILE レコードからパスを復元。QuickFolderSize の MFT 知識は参考にするが、入力は raw セクタ
7. `file_copy_out` — non-resident データランを読んで別ドライブへ。ソースへ WriteFile しない
8. `letter_assign` — `SetVolumeMountPoint` / `DefineDosDevice` 相当。対象が Healthy NTFS のときだけ

不良セクタ・サイズ不一致があっても診断は最後まで走らせ、止めない。失敗は行単位で残す。

検査モード `QUICKAPPSTEST=1` では実 PhysicalDrive を開かず、指定イメージファイルだけを対象にする。

## 検証方法

1. 合成イメージで GPT 不一致を検出し、JSON に primary/backup の LBA・容量が分かれて出る。
2. 合成 NTFS でファイル 3 個を copy-out し、内容が一致する（ハッシュ）。
3. イメージ保存がソースを `GENERIC_READ` のみで開く（コードレビュー + テストで Write パスがソースハンドルに無い）。
4. GUI 起動（管理者）。ダーク UI、日英切替、バージョン情報、読取専用表示。
5. `{type:"ping"}` → `{type:"pong"}`。`QUICKAPPSTEST=1` で実ディスクを触らない。
6. CLI `diagnose` がイメージパスを受け、終了コード 0 と JSON を返す。
7. 画面に初期化・フォーマットが無い。
8. 実機の壊れた D: は **この計画の合格条件にしない**（別 PC 復旧中。イメージが手元に来たら別計画で読む）。

失敗したら失敗と原因を `plans/2026-09-09_初期実装_結果_v1.0.md` に書く。捏造しない。

## リスク

- 未マウント NTFS の MFT パーサは欠陥が多い。v1.0 は「読めたレコードだけ救出、読めないは明示」であり、全ファイル保証ではない。
- 不良セクタのある実ディスクをイメージするとさらに悪化しうる。UI に「ソースへは書かないが読み込み負荷はある」と出す。
- GPT 修復を急ぐとバックアップ側の正しいヘッダを潰す。だから v1.0 では書かない。
- 管理者権限アプリなので、保存先をソースディスクに選ばせない（ディスク番号で拒否）。
- QuickFolderSize の MFT コードを無改変コピーするとマウント前提のまま reverse する。raw 用に新しく書く。
